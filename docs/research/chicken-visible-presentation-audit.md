## Asset Registration And Shared Seams

- `matchAssets.ts` is the existing Match asset boundary. It owns stable normal/green chick, normal-claim SFX, and per-player chicken key names; `preloadMatchSliceRuntimeAssets` can load registered images or audio, but its production runtime asset list is currently empty. [matchAssets.ts:21-63](../../src/scenes/matchAssets.ts#L21-L63)
- The asset-registration behavior is covered by tests for stable keys, loader forwarding, generated texture dimensions/colors, and no regeneration of an existing key. This makes `matchAssets.ts` the lowest-risk place to register first authored Match assets while retaining deterministic texture-key behavior. [match-assets.test.ts:45-131](../../tests/match-assets.test.ts#L45-L131)
- `generateTextureOnce` is shared by Match and Podium. It skips an existing key, draws once into Phaser graphics, generates a texture, and destroys the graphics object. Generated textures therefore persist in Phaser's texture manager across scene use and key collisions matter. [textures.ts:17-26](../../src/scenes/textures.ts#L17-L26) [MatchScene.ts:323-343](../../src/scenes/MatchScene.ts#L323-L343) [PodiumScene.ts:178-205](../../src/scenes/PodiumScene.ts#L178-L205)
- The audio seam is likewise shared but procedural: both scenes use `createSceneAudioAdapter`, which schedules the typed SFX moments through WebAudio when a context exists and otherwise records the play without output. Match maps three IDs to normal claim, green appear, and green claim moments; Podium maps its fanfare ID. [scene-audio.ts:4-30](../../src/audio/scene-audio.ts#L4-L30) [MatchScene.ts:62-68](../../src/scenes/MatchScene.ts#L62-L68) [PodiumScene.ts:150-158](../../src/scenes/PodiumScene.ts#L150-L158) [sfx.ts:29-163](../../src/audio/sfx.ts#L29-L163)
- There are no committed runtime art or audio files under `public/assets/`; the manifest states that current presentation uses procedural Phaser textures and generated WebAudio fallback sounds. Any first asset commit must record path, creator, source, license, and runtime usage. [manifest.md:1-20](../../public/assets/manifest.md#L1-L20)

## Runtime Constraints And Preservation Boundaries

- The game renders at a 1600x1200 backing resolution with `WORLD_SCALE = 2`; absolute scene geometry is authored as base pixels multiplied by that constant, and Phaser is configured with antialiasing, rounded pixels, Arcade physics, and FIT scaling capped to the backing size. New sprite dimensions, origins, and pixel treatment need to work at that scale. [main.ts:6-31](../../src/main.ts#L6-L31) [layout.ts:30-36](../../src/match/layout.ts#L30-L36)
- Match gameplay is owned by `Match`: it advances timing and occupancy, accepts `claim(spotIndex, playerIndex)`, returns discrete events, and exposes only a renderable view of scores, completion, normal chicks, anticipations, and green chick state. Scene art should consume this interface rather than introduce visual state that decides claims, timing, scores, or winners. [match.ts:54-75](../../src/match/match.ts#L54-L75) [match.ts:111-205](../../src/match/match.ts#L111-L205)
- The current scene maintains collision correctness by creating overlaps between each player sprite and every pooled normal chick plus the green chick. A visual replacement must not change which sprite bodies are enabled or the match calls made by those callbacks. [MatchScene.ts:530-578](../../src/scenes/MatchScene.ts#L530-L578)
- Match-to-podium data is the preservation seam for ceremony behavior: after completion, the Match scene waits 500 ms and passes scores, winner, colors, and bot slots to `PodiumScene`. Presentation changes must retain this handoff and must not change completion timing or result data. [MatchScene.ts:246-259](../../src/scenes/MatchScene.ts#L246-L259)
- The approved initial art slice intentionally limits scope to a shared recolorable player base, normal yellow chick, a small number of hiding spots, low-contrast stadium framing, normal claim feedback, and authored normal-claim SFX. It explicitly excludes green-chick art/fanfare and podium polish. The requested chicken-visible audit includes both screens, but that brief remains the present scope boundary for any follow-on implementation. [art-audio-slice-brief.md:7-21](../art-audio-slice-brief.md#L7-L21) [art-audio-slice-brief.md:31-39](../art-audio-slice-brief.md#L31-L39)

## Likely Shared Assets

1. **Player Chicken base:** one recolorable, animation-capable asset is needed by both scenes because Match currently has a detailed procedural chicken and Podium has only a colored circle. Preserve the four central player colors and player-specific facing/placement at the scene layer. [MatchScene.ts:398-499](../../src/scenes/MatchScene.ts#L398-L499) [PodiumScene.ts:281-295](../../src/scenes/PodiumScene.ts#L281-L295) [colors.ts:1-23](../../src/setup/colors.ts#L1-L23)
2. **Normal Chick:** `match.chick.normal` is already a stable registered key and a pooled physics sprite source. A replacement should target that key or an equivalent registration seam. [matchAssets.ts:38-45](../../src/scenes/matchAssets.ts#L38-L45) [MatchScene.ts:508-518](../../src/scenes/MatchScene.ts#L508-L518)
3. **Hiding Spot assets:** bushes and hay bales are the brief's first named asset candidates and already exist as layout types, making them the lowest-risk first replacements. The remaining four types should retain their layout anchors until their art is separately validated. [art-audio-slice-brief.md:9-12](../art-audio-slice-brief.md#L9-L12) [layout.ts:6-16](../../src/match/layout.ts#L6-L16)

Generated WebAudio is explicitly fallback scaffolding.
